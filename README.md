# 🥗 Diet Manager

A web app for quickly and easily checking the personalized diet plans of multiple family members — designed to be opened on the fly while cooking, without digging through PDFs or printed sheets.

> **Project status**: working MVP — read-only, no writes from the frontend.

---

## 📖 The problem it solves

Diet plans typically arrive as PDFs generated by nutrition software (in this case Dietosystem), organized by day of the week. Checking them every day — especially for multiple family members — means opening and scrolling through long PDFs each time.

Diet Manager takes that data, structures it in a database, and immediately shows **the right meal for the current time and selected person**, with the rest of the day available a tap away.

---

## ✨ Features

- **Person selector** — switch between multiple family members' diet plans with a tap
- **Automatic detection** — on load, the app shows the current day on its own and opens the meal matching the current time slot
- **Day navigation** — scroll forward and backward through the days of the week to check ahead or review past days
- **Collapsible meal cards** — the current meal is expanded by default, others stay compact and expand on tap
- **"Free meal" handling** — meals with no specific prescription (e.g. Saturday dinner) are handled as a distinct case, without showing empty or misleading data

```
│   └── SelectPersona.tsx      # person selector
│
├── pages/
│   └── Home.tsx                # main screen, composes the components above
│
├── hooks/
│   ├── usePersone.ts           # fetches people from the database
│   └── useDietPlan.ts          # fetches the diet plan for a person/day
│
├── lib/
│   ├── supabaseClient.ts       # Supabase client initialization
│   ├── days.ts                 # list of days + current day calculation
│   ├── mealTimeRanges.ts       # time ranges for detecting the current meal
│   └── groupMealsByType.ts     # groups flat DB rows by meal type
│
└── App.tsx
```

The UI is split into two levels: **generic** components (`Button`, `FoodItem`) that know nothing about the app's domain and receive everything via props, and **domain** components (`MealCard`, `SelectPersona`) that know what a meal or a person is, but still stay "dumb" regarding data source — they don't fetch on their own, they receive data from outside.

## 🗄️ Data model

The database is organized into 6 relational tables:

```
persona ──┐
          ├──< pasto >── tipo_pasto
giorno ───┘      │
                  └──< pasto_alimento >── alimento
```

- **persona** — who follows the plan (e.g. Manuel, Silvano, Anna)
- **giorno** — the 7 days of the week
- **tipo_pasto** — breakfast, snack, lunch, dinner etc., with their time ranges
- **alimento** — controlled vocabulary of every food item appearing in the plans
- **pasto** — a concrete occurrence: that person, that day, that time slot
- **pasto_alimento** — detail rows: what and how much, for each meal

A view (`v_piano_alimentare`) joins all tables into a single readable row for querying, used directly by the frontend.

## 🧪 Testing

The project uses **Vitest** with **React Testing Library** for the most critical tests: the automatic day/meal detection logic (the most delicate part, since a bug here shows the wrong meal without it being visually obvious), the grouping of database rows, and the interactive behavior of the main components (day navigation, meal card expand/collapse).



**What's covered:**
- `lib/mealTimeRanges.test.ts` — correct meal detection based on time, including edge cases at time slot boundaries
- `lib/days.test.ts` — correct calculation of the current day of the week
- `lib/groupMealsByType.test.ts` — grouping of database rows by meal type
- `components/DayNavigator.test.tsx` — forward/backward day navigation, including wrap-around between Sunday and Monday
- `components/UI/MealCard.test.tsx` — meal card expand/collapse behavior

## 📦 Deploy

Deployment to GitHub Pages is automated via GitHub Actions: every push to the `main` branch triggers a build that automatically publishes the new version.

Environment variables for the build are provided via **GitHub Secrets** (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`), not included in the repository.
